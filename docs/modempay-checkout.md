# ModemPay cash-in

ModemPay is used only to fund Sutura wallets. Merchant purchases continue to
use a Sutura wallet; no guest or external merchant checkout API is exposed.

Online cash-in opens ModemPay hosted checkout with mobile money or card. The
backend fixes the destination wallet, currency, amount and Sutura reference.
It requires a GMD wallet, at least GMD 10 and at most two decimal places.
Agent cash-in retains its existing internal QR workflow.

## Configure

Rotate any API key shared in chat. Create a restricted key with payments:write.
Configure the live webhook in ModemPay Developers → Webhooks:

```text
https://suturagambia.onrender.com/api/v1/webhooks/modem-pay/charges
```

Copy the signing secret generated by ModemPay after saving that URL. An existing
random server secret cannot replace it; changing the webhook URL generates a
new secret. Put these in Render Environment and the ignored server/.env:

```dotenv
MODEMPAY_ENABLED=true
MODEMPAY_API_KEY=<replacement secret key>
MODEMPAY_WEBHOOK_SIGNING_SECRET=<live webhook signing secret>
MODEMPAY_API_URL=https://api.modempay.com
MODEMPAY_WALLET_RETURN_URL=suturaapp://payment-return
MODEMPAY_PAYOUTS_ENABLED=false
```

No secret key goes into the mobile app or website. A public key is not required
for this server-created hosted checkout flow. Test keys require test webhooks;
live keys require test_mode=false. Meet ModemPay's business verification
requirements and monitor the key's expiry date. Use a separate test environment
for test-mode payments, not a real wallet database.

## Background processing

The webhook checks its raw-body HMAC-SHA512 signature and payment mode, then
commits an authenticated receipt before returning 200. The incoming worker
checks the stored reference, provider charge ID, amount and currency, then asks
Sentinel and credits the wallet through the existing ledger path.

When Sentinel is sleeping or unavailable, cash-in and wallet/merchant transfers
remain pending. Durable jobs retry with increasing delays up to two minutes.
The scoring request snapshot is committed before background scoring, keeping
its timestamp and balance context unchanged across retries and restarts.
Transfer workers also warm Sentinel through its health endpoint before taking
payer locks. No ledger posting executes without a valid ALLOW decision.
Actual BLOCK decisions still stop the payment; REVIEW uses the existing case
approval workflow. Duplicate confirmations never credit twice.

Merchant wallet payments queue immediately and show PROCESSING while waiting;
they show REVIEW only after an actual review decision. Neither redirects nor
connection failures manufacture a successful payment or a fraud score.

Do not automatically replay a checkout charge. Background processing retries
risk evaluation and settlement of an already confirmed payment, not the
external collection. Unmatched provider events are retained as ignored receipts.
Administrative native-webhook replay uses the same authenticated inbox path.

Migration V20 adds persistent retry timing and scoring snapshots; normal backend
Flyway deployment applies it. Background workers are enabled by default. Tests
disable scheduled execution and invoke processors explicitly for determinism.

## Validation

Tests cover cold-start recovery, genuine blocks, merchant wallet processing,
durable cash-in acknowledgment, duplicate callbacks, payment-mode mismatches,
scoring snapshots, wallet limits and ledger idempotency. Finish provider testing
after credentials and the webhook are configured. Confirm both the provider
transaction and Sutura's ledger; returning to the app alone proves no payment.
