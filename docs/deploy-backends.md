# Deploy Sutura and Sentinel backends on Render

Use **`render-backend.yaml` in each repository** for this deployment. It creates
only the two Java APIs, one shared PostgreSQL database, and Sutura's Key Value
cache. Do not also apply `render-free.yaml` or `render.yaml` to the same deployment;
those files describe alternative resource sets, including frontends or paid plans.

## 1. Complete the private environment files

From the parent workspace containing both separate repos:

```powershell
python sutura/server/deployment/prepare-render.py --sutura-url https://suturagambia.onrender.com
```

This prepares **`sutura/server/.env.render`** and **`sentinel/.env.render`**.
Each backend uses its single `.env.example` template; no separate Render example
file is needed. The script selects Render-specific defaults from that template.
They are ignored by Git. Existing nonempty secrets are preserved; matching
integration keys and webhook secrets are generated once. Your local Jokoor key is
copied from `sutura/server/.env` if the Render file's key is empty. No SMS, emails
or payments are sent. Never upload either file to GitHub.

Fill the settings reported by the command. In particular, supply the actual
Resend key, verified email sender, operations inbox, ModemPay API key, first
admin email and international phone. The ModemPay signing secret in the file
must also be configured for the webhook at ModemPay. Provider keys are not
generated by this tool. Do not use example frontend domains as CORS origins.
The generated admin passwords are in the private files, not in command output.

Run a read-only check any time:

```powershell
python sutura/server/deployment/prepare-render.py --check
```

Some entries cannot be completed until Render assigns the API URLs and database
connection details. The check deliberately reports them as incomplete rather
than making up values. The two API repos must be pushed before Render can build
the new deployment configuration.

## 2. Create the resources

1. In Render, create a **Blueprint** from the **Sutura** repository. Set the
   Blueprint path to `render-backend.yaml`. Review the three resources:
   `suturagambia`, `sutura-db` and `sutura-cache`, all in Frankfurt. Enter its
   prompted values from `server/.env.render`. If the datastore already exists,
   reuse it rather than trying to create a second free datastore.
2. Create a separate Blueprint from the **Sentinel** repository, also using
   `render-backend.yaml`. Enter the **same database's** internal hostname,
   database name, username and password. Copy them from `sutura-db` in Render
   into `sentinel/.env.render`. Use port 5432. Do not paste a complete database
   URL into `RENDER_DB_HOST`.
3. Copy the actual HTTPS origin assigned to each API. Update the private files
   with the correct Sentinel origin and Sutura callback:

   ```powershell
   python sutura/server/deployment/prepare-render.py --sutura-url https://YOUR-SUTURA-API.onrender.com --sentinel-url https://YOUR-SENTINEL-API.onrender.com
   ```

4. Import the matching `.env.render` file into **each API service's Environment**
   settings, save and redeploy. Sutura's database/cache bindings are supplied by
   the Blueprint and intentionally omitted from its env file. The generated
   `JWT_SECRET` overrides Render's initial generated key when imported: do this
   before users sign in, and then retain the same key on later deployments.

Create both services before completing their cross-service URLs; the first
deployment may fail until those values are corrected. Do not bypass startup
validation to make an incomplete configuration appear healthy.

Sutura runs `prod,render,render-free`; Sentinel runs `render`. Dockerfile paths
and contexts are already declared in the Blueprint. No manual build or start
command is needed. Both bind Render's `PORT`.

## 3. First accounts and health

The private files enable first-deployment account bootstrap. Sutura creates its
first admin; Sentinel creates the `sutura` tenant, its admin and the matching
integration API key. No demo users are seeded. Existing accounts are never reset
by this bootstrap. After the first successful startup, set the two bootstrap
enabled flags to `false` in Render and remove their admin passwords. Preserve
Sentinel's field encryption key, JWT secrets, database credentials, and Sutura's
integration key/webhook secret. Re-running the preparation tool must not be used
to reset an existing account's password.

Render health checks:

| API | Path |
| --- | --- |
| Sutura | `/actuator/health/readiness` |
| Sentinel | `/actuator/health` |

Both must report `UP`. Sutura's readiness includes PostgreSQL and Key Value.
Then run the read-only smoke check with your actual frontend origin:

```powershell
python sutura/server/deployment/smoke.py --api-url https://YOUR-SUTURA-API.onrender.com --origin https://YOUR-CUSTOMER-FRONTEND
```

Live SMS/email delivery, sign-in 2FA and payment/webhook acceptance still require
testing with your own configured providers. Local `.env` files are not
automatically read by Render or by `java -jar`; import/export the settings.

## 4. Add Hugging Face later

Sentinel's backend-only Blueprint sets **`SENTINEL_ML_ENABLED=false`** and keeps
ML stubs disabled. Auth, tenant administration, existing records and health can
run without model URLs. New liveness challenges, identity/document inference and
transaction ML scoring return **503** until real ML is enabled. Sutura may stop
operations that require these risk checks; missing ML is never a successful
verification or a safe transaction decision.

After deploying both ML services, set `CV_ML_BASE_URL`,
`TRANSACTION_ML_BASE_URL` and the same `ML_SERVICE_API_KEY` used by those services
on Sentinel. Set `SENTINEL_ML_ENABLED=true` and redeploy. Configure
`SENTINEL_PUBLIC_BASE_URL` to the actual hosted KYC frontend before using hosted
links. ML readiness and model evaluation are separate from Java API health.

## Hosting limits

This is a free-host deployment configuration. Render's free PostgreSQL expires
after 30 days; free APIs can sleep, free Key Value data is volatile, and free web
services have no persistent disk. Sentinel evidence stored on the API filesystem
will be lost on restart/redeployment. Use non-sensitive samples until durable
evidence storage and backups are configured. See
[Render free service limits](https://render.com/docs/free).
